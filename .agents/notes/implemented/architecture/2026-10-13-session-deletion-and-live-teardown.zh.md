# Agent Note: 会话删除与活动会话拆除

Status: implemented

[English](2026-10-13-session-deletion-and-live-teardown.md) | 中文

## 问题

本 harness 一直没有任何删除已存储会话的手段。归档是唯一具备“可恢复”形态的操作，而它从不触碰文件：它只是把一个 id 追加到持久化的 `archivedSessionIds` 集合里。持久化接缝与侧边栏都把这写成了限制——“No deletion or retention API”与“No Session deletion”——因此想让某条对话及其日志消失的用户只能绕到文件系统外面去处理，而那要求知道部署的存储根目录和项目目录的编码规则。

加入删除并不只是执行一次 `rm`。进程内活着的会话持有打开着的持久化写句柄，后端按 id 把该会话的事件路由进去，所以先删文件只会在下一个事件到来时把它们重建出来。客户端的会话列表是活动注册表与持久化 listing 的合并结果，因此保持活动的会话会在日志已消失之后继续保留自己的行。而 API 宿主中没有任何东西能让一个会话变为非活动：`create` 与 `resume` 会返回一个 `AgentHandle`，它的 `dispose()` 会停止循环、注销 agent、并把该 session 从 store 中移除——但宿主把它丢掉了，只保留 `.agent`。打开一条对话的历史就会把它提升为活动 agent，因此实际上用户能看到的几乎每一行都是活动会话。

## 决策

**删除是持久化能力，而接缝只负责移除。** `SessionPersistence.delete(id)` 移除后端为某一个会话拥有的全部产物——完整存储日志（所有保留代）、会话目录，以及其中的写锁文件——此外别无其他。它幂等（后端看不见的 id 直接 resolve，因为移除的后置条件已成立），并且绝不触碰与其他会话共享的内容寻址产物：附件没有 session→object 的反向索引，所以后端无法知道删除某一个是否会破坏另一个会话，它也不做这种尝试。移除哪些会话始终由调用方决定；接缝中没有任何机制按龄淘汰会话，也没有批量剪枝。

**打开中的写句柄被拒绝，关闭中的被等待。** 只要本实例持有该 id **打开中**的写句柄，随附的提供方就以 `SessionPersistenceActiveError` 拒绝，因为实时写入路径会把日志重建出来。已经处于关闭中的句柄则被等待而不是被拒绝。这一不对称是承重的：提供方的 `session/disposed` 监听器会启动最终排空并调用 `handle.close()`，但**不 await 它**，因此先销毁会话、紧接着删除的调用方，否则会被一次仍在途的关闭挡回去——而这正是宿主执行的顺序。

**API 宿主保留每个 Agent 的拆除能力。** `ApiSessionAgentController` 把 `agents.create`/`agents.resume` 返回的 `AgentHandle` 按会话 id 记在一个 map 里，并在该 Agent 被销毁时删除条目（一个 `agent/disposed` 监听器会清理并非由本控制器亲自销毁的句柄）。`disposeLive(id)` 取出并销毁句柄：停止循环、等待其退出、注销 Agent、从 store 中移除该 Session、并解开它的 scope。这是让会话变为非活动的唯一路径，因此它是移除日志的前提条件，而不是一项优化。

**`session.delete` 把步骤排序成文件无法复活的形式。** 命令以 `session/archived` 拒绝已归档的会话（归档才是可恢复状态，所以用户先恢复再删除），拒绝属于 subagent 路由的会话，并且在调用方未设置 `stopActivity` 时以 `session/active` 拒绝仍有工作在跑的会话并列出这些工作。随后它通过与归档准入相同的 `workspace/session-stop` 事件停止运行中的工作，销毁活动 Agent，调用 `sessionPersistence.delete`，删除投影缓存检查点，调用 `WorkspaceRegistry.forgetSession` 移除归档条目、置顶、记账槽位与已索引头部，并向已连接的客户端宣告该移除。从未活动过的会话不会发出 `session/disposed`，因此命令只在这种情况下自行宣告；被销毁的会话已经通过既有监听器宣告过了。

**删除不级联。** 分叉与子代理派生的子会话在其父会话被移除后依然存在。存活的子会话保留一个指向已不存在会话的 `parentSession`，而代码库对此本就容忍：lineage 追踪返回 `complete: false` 与 `unresolvedParentId` 而不是抛错，subagent 控制面有专门的 `subagent/parent-unavailable` 错误码，父 catalog 发现也早已把缺失的子项降级为 unknown 模式。级联被拒绝的原因是：分叉本身就是一条用户可见的对话，而删除一行悄然摧毁其他几行，比一个界面已经知道如何渲染的悬空指针是更糟的失败。

**注册表在不暴露集合的前提下回答归档问题。** `WorkspaceRegistry.isArchived(id)` 的存在使删除命令可以基于一个读取方法分支，而不必伸手去读 `archivedSessionIds`，从而让归档集合在注册表中保有唯一的家。`WorkspaceRegistry.sessionActivity(id)` 暴露归档准入所读的同一条 `workspace/session-activity` waterfall，使客户端的确认框能列出确认后将会停止的工作——这是一次读取而非准入检查，不安装任何状态。

**客户端总是确认，且从不提供悬停按钮。** 删除不可撤销，因此它留在行的「...」菜单中，用分隔线排在归档之下，且不在 `sidebar.workspaces.session.row.action` 中注册。选中它会打开一个写明不可撤销的对话框，向宿主询问该会话正在运行什么，若有则列出这些类别；确认按钮先停止这些工作再删除。已归档行在对话框打开之前就被拒绝——菜单项仍然可见，但选中它会触发「请先取消归档」——当并发的归档赢得竞态时宿主以同样方式拒绝。删除主视图中的会话会清除选择，使视图回到所属工作区且不选中任何会话，而不是打开一条用户并未要求的无关对话。删除成功会弹出一条没有撤销操作的提示，因为没有什么可撤销的。

**离开被放弃的「无记录」会话时移除它。** 一条从未开始过轮次的会话一旦不再是当前空白行就不可触达：导航隐藏所有非当前空白行，空白行也不渲染任何动作，因此 `session.delete` 永远够不到它，而每点一次「新建会话」都会留下一条存储日志。主视图导航因此在离开时评估这条会话：宿主报告它为空白、它不在归档集、没有独立的引用方持有它、且其 composer 没有草稿、暂存附件、队列消息或进行中的提交时，客户端调用 `session.delete`。右侧栏镜像主选择而持有的引用不计入——该镜像视图退役、其已提交挂载卸载后即释放。清理失败只记日志，绝不让导航失败。composer 这道闸是承重的——该行被隐藏且无处可达，丢掉已输入的内容等于毁掉它且无法找回。

判据是「没有 `turn/start`」，而不是裸的 `seq === 0`。新建会话会把权限预设、沙箱模式与审批策略作为最初几个事件写入，因此日志在用户输入任何内容之前就已到 seq 2；零事件判据会把恰恰要清理的这些会话判定为「有记录」。宿主的 `blank` 值就是该判据。

## 考虑过的替代方案

**在 `delete` 内部强制关闭后端的写句柄。** 后端可以在 `delete` 中作废活动句柄并移除文件，调用方就无需再做别的事。被拒绝：这留下一个活着的、不可达的 Agent——`ctx.agents.get(id)` 与 `ctx.sessions.get(id)` 继续给出答案，`session/disposed` 永不触发因而投影缓存的 detach 写入与客户端的行都会泄漏，仍在注册的回合继续发出无处可去的事件。store 会与磁盘相互矛盾，而这正是本 harness 在其他地方拒绝进入的状态。

**对任何本进程内活动的会话拒绝删除。** 这是最小的改动：不保留句柄，不动生命周期。因其不可用而被拒绝——打开一条对话就会把它提升为活动 agent，所以用户最想删掉的那些行恰恰是它要拒绝的，而且没有其他方式卸载它们。

**级联到分叉与子代理派生的子会话。** 上面已拒绝：它把一次确认变成对用户可见对话的静默摧毁。

**在空白行上渲染行操作，让删除能够触达，以此替代「离开导航即断开」。** slot 契约本就允许条目在其动作不适用于该行时什么都不渲染，因此四个随附动作可以各自退出、把删除单独留在菜单里。对被放弃会话的清理而言被拒绝：这会在整个含义就是「什么都还没发生」的占位行上放一个只有单项的破坏性菜单，而且所有*未选中*的空白行依然不可见，用户最想清掉的那一行依旧触达不到。

**把会话目录移动到回收站位置而不是移除。** 这是推迟而非拒绝。它只会改变 `delete` 的实现——移动而非移除——对其余链路毫无影响，因此如果用户要求恢复窗口，它仍然可用。

**把删除接缝改名挂到 Workspace 注册表上，与 `archiveSession` 并列。** 被拒绝：删除会话是会话生命周期操作，而唯一能持有 `AgentHandle` 的地方是 API session controller。Workspace 注册表贡献的是元数据清理（`forgetSession`）与活动读取，那才是真正属于它的部分。

## 后果

侧边栏能显示的每一个会话现在都可删除，包括用户正在查看的那一个，代价是 API 宿主中一次真正的生命周期变更：它开始持有此前被丢弃的 `AgentHandle`，而关闭一个会话现在成为消费方可以请求的能力。这份持有是承重部分——句柄缺失或被清理会降级为 `session/delete-unavailable` 拒绝，而不会产生一个删到一半的会话。

删除在其四个参与者之间并非原子操作。存储日志、投影检查点、Workspace 注册表元数据与活动 Agent 是按顺序移除的，日志已消失之后的失败会留下未完成的后续步骤：命令会如实上报，而不是假装无事。因此投影缓存的 `delete` 会抛错，而不遵循该包「每一次持久写入都是 fail-soft」的规则，因为没有任何机制会为已不存在的会话重写该行——吞掉失败会把调用方想要回收的产物泄漏下来。

子代理来源的会话不能经由这条路径删除：subagent manager 持有自己的 disposer，而 API 宿主本就拒绝它们。删除子代理子会话是另一项所有权变更。

会话格式版本不受影响。删除只移除产物；它不改变已存储的 header 或事件词表，因此不随之带来迁移或升级指南条目。*迁移*所提交的代文件依然永不重命名、替换或删除——`delete` 移除的是整个会话目录，那是对会话的用户主动操作，而不是对某个已提交代的搬动。
